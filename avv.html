1. Scope & Roles

This DPA applies to Scandora's processing of your document content, and of data derived from it, on your behalf. That processing happens on five paths:

  • Managed AI — the AI features: document analysis, the search index and document chat. Document analysis: your device calls the AI model provider with a short-lived credential (up to 30 minutes) that Scandora's server issues and sends the page images or the text of the document being analysed. Search index: Scandora's server builds a search index from the text of your stored history records and keeps it on Scandora's own server in Falkenstein, Germany, next to those records; to build it, the server automatically sends the extracted text and the AI description of each new document, split into passages each headed by the document's title, type and date, to the model provider, which returns the search vectors, and the server stores the passages with their vectors. Document chat: to answer a chat question, the app sends the question and the earlier messages of that chat to Scandora's server, which sends the question to the model provider for its search vector, selects matching passages from your index and sends the question, the earlier messages and those passages to the model provider for the answer; the server does not store the question or the answer. On the EU route (the default) the model provider is Google (Vertex AI, europe-west3, Frankfurt). Managed AI is the only AI path in this version: a bring-your-own-API-key option is not part of this version (section 6 of our Terms). Where your user has turned on “AI models outside the EU”, document analysis and chat can instead be answered by Anthropic in the USA: the request then goes through Scandora's server in Germany, which forwards it and neither stores nor logs the page images, the document text, the question or the answer (section 5). The search index is always built with Google, never on that route.
  • Cloud history sync — while you are signed in, each completed scan's history record is uploaded to Scandora's own server in Falkenstein, Germany, so your history is available on all your devices. It carries the record's metadata and the full text extracted from the document. The record is stored readable, so that it can be shown on each of your devices and the search index can be built from it. This happens on every plan; it is not optional.
  • Server-side DATEV export — when you run a DATEV export, the booking rows you export and the document images attached to them are sent to Scandora's own server in Falkenstein, Germany, assembled there into the DATEV EXTF ZIP and returned to you. The booking rows carry, per booking, the date, the gross amount, the debit/credit marker, the account and contra account, the DATEV BU key, the invoice number, the booking text, the recognition confidence and the document file name; the export header carries your Berater and Mandant number, the chart of accounts, the fiscal-year start, the exported date range and the name you set as the exporting user. Everything is processed for that one request and is not stored. This export is coming soon: it is designed for the Business and Enterprise plans and is not yet switched on. Until it is, the app shows it as coming soon and no export can be started, so no data travels this path yet; we describe it here because it is contracted for and will be switched on under this DPA.
  • GoBD capture and change records — while you are signed in, every capture, metadata edit, export and deletion also writes a record to Scandora's own server in Falkenstein, Germany, so that a captured document and each later change to it stay traceable: a capture record (a SHA-256 checksum of the captured file, the capture source, a device description, the user and profile identifier and a server timestamp) and a change-log entry (the document identifier, the event — capture, edit, export or delete —, the user identifier, the acting profile, a server timestamp, for an export the destination you exported to, and, for an edit, the old and the new value of each metadata field that changed: title, labels, gross amount, invoice number, invoice date). When Scandora's server deletes history records itself, once the retention period in section 2 has run out, it writes one change-log entry per deleted record, also while you are signed out, with the document identifier, the event delete, the user identifier and the time of the deletion, but no acting profile and no field values. Neither record holds a page image or the document text. This happens for every signed-in user on every plan; it is not optional, and the change log is append-only at database level — see section 2 for what that means for erasure.
  • Cross-device import register — when you import a document from a connected cloud storage (Google Drive, Dropbox, OneDrive, Nextcloud, Trello) or from your device's file picker, Scandora records that one import centrally, so a second device cannot import the same file again. Unlike every other path above, this record is not stored on Scandora's own server: it is stored in Google Firestore, in the Frankfurt (europe-west3) region. It holds the source identity (the provider, an identifier of the source account, and the provider's file identifier and version marker — or, for a file you picked on the device, a SHA-256 fingerprint of that file's content), your account and profile identifier, the import status, the status and storage reference of each destination the import was delivered to, and a short-lived device lease. It holds no page image and no document text. The storage reference is the destination's file URL or the generated PDF's file path and can therefore contain the document's file name. It is written on every plan whenever you use an import; importing the same file again removes its entry, and account deletion erases every entry of the account.

If Scandora later adds a further path on which your document content is processed on your behalf, we inform you in text form before that extension takes effect and update sections 3 and 5 accordingly. You may object before it takes effect. If you object, we do not activate the new path for your account and this DPA continues unchanged for the paths listed above. Where we cannot provide the service to you without that path, we tell you when you object, and you may then terminate this DPA and the underlying contract with effect from the date the extension would have taken effect. You are never left using Scandora for your clients' data without a contract under Art. 28 GDPR in force. If you do not object, this DPA covers the new path from that date.

Your own account data — your email address, your name, your subscription and billing record — sits outside this DPA. For that data Scandora is the controller under its own contract with you, not your processor. The same is true of email correspondence; see the note under section 5.

Feedback on AI answers also sits outside this DPA. When one of your users rates an AI chat answer, the app sends the rating, the chosen reasons, an optional note and details about the answer, such as the model and the app version, to Scandora's own server in Germany; only if the user ticks a box for that one rating does it also send the question and the answer, which can quote the document. Scandora processes this feedback as controller, for its own purpose of improving its AI answers, as set out in section 2 of our Privacy Policy; it is not part of the managed AI path above. Where your users work with your clients' or customers' documents, instruct them not to tick that box for those documents.

Who is controller of the history record. The history record is covered by this DPA in full — the extracted document text and the record's metadata (title, dates, page count, file size, labels, export destinations, extracted fields). You decide which documents are scanned and why they are kept, so Scandora stores that record as your processor and uses it for no purpose of its own. Section 8 of our Privacy Policy lists history metadata under Scandora's controller role; that describes use without a DPA, where the user is a data subject rather than a controller. For the records you process under this DPA, the processor role stated here applies. The same applies to the search index built from those records.

  • Controller: you (the business customer / your Steuerberater's client).
  • Processor: Scandora — Farhad Sanaei seresht (sole proprietor, trading as "Scandora"), Burgunderweg 19G, 22453 Hamburg, Germany. See our Imprint.
  • Sub-processors: the hosting provider of Scandora's EU server (Hetzner); Google (Gemini API / Vertex AI, Frankfurt) as the model provider for document analysis, for the search vectors of the search index and, by default, for chat answers; Google Firebase, which stores the import register; and, only for users who have turned on the optional route to AI models outside the EU, Anthropic Ireland, Limited, whose processing runs in the USA — see section 5.

2. Subject, Nature, Purpose & Duration

Processing lasts for as long as you use Scandora and ends when the underlying contract ends. Per path:

  • Managed AI — for document analysis, your device sends document images, extracted text and prompts to the AI model provider, using the short-lived credential described in section 1. For the search index and for chat, Scandora's server sends the model provider the chat questions with the earlier messages of a chat and the passages it selected from your index, and, when a document is indexed for search, its extracted text and AI description, split into passages each headed by the document's title, type and date. The model provider processes this content to produce AI results (e.g. titles, labels, extracted fields, the search vectors of the index and chat answers) and, apart from the abuse monitoring described below, does not retain it beyond the request. The processor stores the search index — the passages and their search vectors — on Scandora's own server next to the history record it was built from, and for no longer than that record: deleting the record, the end of its retention period in the next item or the deletion of the account erases its passages with it. Scandora's server does not store the chat questions or the answers. On the optional route to AI models outside the EU (section 1), Scandora's server in Germany sends the content to Anthropic in the USA instead and neither stores nor logs what it forwards; Anthropic uses it only to produce the answer, does not train its models on it and deletes inputs and outputs within 30 days; if a request is flagged for a usage-policy violation it may keep it for up to 2 years, and longer only where the law requires it.
  • Cloud history sync — the processor stores the history record described in section 3 to keep your scan history available across your devices. Retention: on the Free plan each record is erased 180 days after it was stored; on a paid plan no record is erased while the subscription is running, and the window starts when the subscription ends — 90 days (Pro), 180 days (Business). A subscription taken up again inside that window leaves the records in place. Records that were already stored when this deletion was switched on run their window from that switch-on date. A record you delete is erased with that deletion; when the account is deleted, every record of that account is erased with it, at the latest within 30 days.
  • Server-side DATEV export (coming soon — not yet switched on, see section 1) — the processor receives the booking rows you export and the document images attached to them, assembles the DATEV EXTF ZIP and returns it to you. This is transient: neither the rows nor the images are stored.
  • GoBD capture and change records — the processor stores these records as evidence that a captured document is unaltered and that every later change to it is traceable. They are not erased when you delete the history record or your account: the change log is append-only at database level, so single entries cannot be deleted, and the capture records are kept alongside it so that a document's origin stays verifiable. What an account deletion does do is replace the identifiers in them: the user and profile identifiers are replaced by a stand-in value, and the edited metadata values and the exported file names are removed with the account, while the checksum, the timestamps and the hash chain stay, so the records survive without the identifiers they were written with. We do not present the result as anonymous data: each entry's chain fingerprint was computed before that replacement, and the capture record's checksum still matches the document itself, so anyone holding that document or the replaced identifiers can still tie an entry to a person. Why we keep them, plainly: no German law requires us to store them. The GoBD record-keeping and unalterability duties (§ 146(4), § 147 AO, § 239(3) HGB) bind you or your business, not us, and § 257 HGB binds merchants, which Scandora — run as an unregistered sole proprietorship (Kleingewerbe) — is not. We therefore do not rely on Art. 28(3)(g) GDPR, which lets a processor keep data past the end of the contract only where Union or Member State law requires that storage. We keep these records for our own evidence purpose and are the controller for that retention (Art. 6(1)(f) GDPR): a document captured with Scandora should stay verifiable for as long as you may have to produce it. They are written on every plan and cannot be switched off — we therefore do not present that retention as an instruction you gave us. How long: we keep both records for ten years, the period German law sets for a trader's own books and records (§ 147(1) No. 1, (3) AO), counted from the end of the calendar year in which the record was made (§ 147(4) AO), and delete them once that period has expired. That period is a cap we set ourselves, not a duty we are under — section 11 of our privacy policy says the same. The delete-or-return duty in section 4 and the erasure measures in section 7 do not reach these two records while that period runs. One limitation, stated plainly: today nothing removes these rows by age. The change log is append-only at database level, so its entries cannot be deleted at all, and no routine yet deletes the capture records when the period expires, so the records currently stay beyond it. Building that deletion step is on our list; we do not warrant a date-certain erasure that we could not carry out. What we cannot do for them: the database rejects every deletion of a change-log entry, and every change to one except a change that carries our account-deletion marker, leaves the chain values and the timestamps untouched and marks the entry as redacted — only the account-deletion routine sets that marker, and a marked entry is no longer checked against its own fingerprint, so a change made through that one path is not flagged as tampering. The capture record's checksum and timestamp are write-once, so we cannot rectify a single entry or erase one, and we do not promise you an earlier erasure that we could not carry out. If your own retention duty ends sooner, tell us in text form: we then use the records for that evidence purpose only and for nothing else (Art. 18 GDPR) and note your objection (Art. 21 GDPR). If you do not want these records written at all, Scandora cannot be used for those documents; you may terminate this DPA and the underlying contract in accordance with that contract. See section 8.
  • Cross-device import register — the processor stores one register entry per import, in Google Firestore (Frankfurt), so the same source file is not imported twice across your devices. The entry is kept for the life of your account: importing the same file again deletes its entry, and account deletion erases every entry of the account. It carries no document content — the field list is in section 3.

Abuse monitoring. Google may keep prompts sent through managed AI that its automated safety systems flag for up to 90 days, in the Google Cloud region used for managed AI (europe-west3, Frankfurt), only for abuse monitoring; Google does not use them to train models.

3. Data Categories & Data Subjects

Categories of data:

  • Document images, the text extracted from them and the prompts about a document — sent by your device to the model provider for document analysis (managed AI, EU route).
  • Chat questions with the earlier messages of a chat and the passages Scandora's server selects from your index, and, when a document is indexed for search, its extracted text and AI description, split into passages each headed by the document's title, type and date — sent by Scandora's server to the model provider (managed AI, EU route).
  • On the optional route to AI models outside the EU, used only where your user has turned it on: the page images or text of the chosen document, the chat question with the earlier messages and the selected passages, and the model's answer — sent through Scandora's server in Germany, which does not store them, to Anthropic in the USA.
  • The history record stored on Scandora's own server: the full text extracted from the document (OCR text, stored up to a 400,000-character cap), together with the record's metadata — title, creation date, page count, file size, labels, the destinations you exported to, and the fields the AI extracted (e.g. amount, invoice number, invoice date).
  • The search index stored on Scandora's own server next to the history records: the passages of each document's extracted text and AI description, each headed by the document's title, type and date, with one search vector per passage.
  • The DATEV export payload (transient; the export is coming soon and not yet switched on, see section 1): the booking rows — per booking the date, gross amount, debit/credit marker, account and contra account, DATEV BU key, invoice number, booking text, recognition confidence and document file name — the export header (Berater number, Mandant number, chart of accounts, fiscal-year start, exported date range, the name set as the exporting user), and the document images attached to those bookings. A booking text or an invoice number can identify your own clients.
  • The GoBD capture and change records: per capture, a SHA-256 checksum of the captured file, the capture source (camera, network scanner or file upload), a device description, the user and profile identifier and a server timestamp; per document event, the document identifier, the event type (capture, edit, export, delete), the user identifier, the acting profile (not for a deletion that Scandora's server makes itself, see section 1), a server timestamp, for an export the destination you exported to, and, for an edit, the old and the new value of each metadata field that changed (title, labels, gross amount, invoice number, invoice date). No page image and no document text.
  • The import-register entry: the source provider, an identifier of the source account, the provider's file identifier and version marker or — for a file picked on the device — a SHA-256 fingerprint of that file's content, your account and profile identifier, the import status, the status and storage reference of each destination the import was delivered to, and a short-lived device lease. No page image and no document text; the storage reference is the destination's file URL or the generated PDF's file path and can therefore contain the document's file name.

All of these may contain special categories of personal data (Art. 9 GDPR) where you submit such documents.

Categories of data subjects: persons you determine, whose data appears in the processed documents (e.g. your clients, customers, employees).

  • Bind authorised personnel to confidentiality.
  • Implement the technical and organisational measures in section 7.
  • Assist you with data-subject requests and with your obligations under Art. 32–36 GDPR.
  • Delete or return the data at your choice on termination (Art. 28(3)(g) GDPR). The GoBD capture and change records described in section 2 are outside that duty: we keep them as controller for our own evidence purpose, for the ten-year period stated there — a cap we set ourselves, not a storage duty imposed on us — and the change log cannot be deleted entry by entry at all.
  • Make available the information needed to demonstrate compliance and allow for audits.

6. International Transfers

Where a sub-processor processes data outside the EU/EEA (e.g. the USA), transfers are safeguarded by the EU Standard Contractual Clauses and/or the provider's certification under the EU–US Data Privacy Framework. On the EU route (the default), managed AI — document analysis called by your device with a short-lived credential Scandora's server issues, and the search index and chat called by Scandora's server — is processed in Germany when the Frankfurt regional service (Vertex AI europe-west3) is used, and is not a third-country transfer for that leg. The optional route to AI models outside the EU, used only where your user has turned it on, is a third-country transfer: the request goes through Scandora's server in Germany to Anthropic, which processes it in the USA under the EU Standard Contractual Clauses (Modules 2 and 3) in Anthropic's data processing addendum, with the UK and Swiss addenda; Anthropic is not certified under the EU–US Data Privacy Framework. Scandora's OAuth components, the credential-issuing endpoint, the search index and document chat run on Scandora's own server in Falkenstein, Germany. Most of the data stored under this DPA — the history records, the search index and the GoBD capture and change records — stays on Scandora's own servers in Falkenstein, Germany. The one exception is the cross-device import register, which is stored in Google Cloud Firestore in the europe-west3 (Frankfurt) region. Both locations are in Germany, so neither store is a third-country transfer; for the remaining Google Cloud processing around it (control plane, support access) the EU Standard Contractual Clauses and/or Google's DPF certification apply.

7. Technical & Organisational Measures (TOMs)

  • Encryption in transit (TLS) on every connection between the app, our servers and our sub-processors.
  • Per-user encryption (AES-256-GCM) of the integration credentials you store. For the remaining data stored under this DPA — the history records, the search index and the GoBD capture and change records — we do not claim encryption at rest as a measure: Scandora's server stores them readable, and they are protected by the access, separation and hosting measures listed here.
  • Separation per user: stored records are held per user and per profile, and every request of the app is checked against the signed-in user's authenticated token. The database itself limits the requests for history records and for the search index to the rows of that user (row-level security), so such a request cannot read or change another user's records even if its own filter is wrong.
  • Staff access to content: Scandora staff can read the content of a stored record only through an administrator view that requires an administrator account, a sign-in confirmed shortly before and a written reason for each record. Every view is written to an audit log before the content is shown, and nothing is shown if that entry cannot be written; the audit log is append-only at database level. Each administrator may open only a limited number of records per day, and an unusual burst of views raises an alert. Administrative access to the server itself is not covered by that log.
  • Administrator requests are refused once the administrator's sign-in has been revoked, and destructive administrator actions, such as deletions, also require a sign-in confirmed shortly before.
  • Request limits per account and per network address on the server's interfaces, including document chat.
  • Pseudonymisation of the user identifier (Firebase UID); the logs of Scandora's services name a user only by a pseudonymous tag; the server's security logs (the access log of the proxy in front of those services, and the login, block and firewall logs) record internet (IP) addresses and times, but not the user identifier and no requested page or query; no log holds document content, a chat question or an answer.
  • Scandora's server does not store or log chat questions or answers, and on the optional route to AI models outside the EU it neither stores nor logs the content it forwards to Anthropic.
  • Deleting a history record removes it and its passages in the search index, and account deletion erases every history record, the search index and every import-register entry of the account. The GoBD capture and change records are retained as described in section 2 and are not covered by that erasure; the account deletion replaces the identifiers in them instead, so no retained entry still stores the deleted account's identifiers.
  • The OAuth components, the credential-issuing endpoint, the search index, document chat and all data stored under this DPA are hosted on Scandora's own server in Falkenstein, Germany, with two exceptions that both stay in Germany: the AI model calls on the EU route go to Google's europe-west3 (Frankfurt) region, and the import register is stored in Google Cloud Firestore in the same europe-west3 region. On the optional route to AI models outside the EU, the AI model call goes through Scandora's server to Anthropic in the USA (section 6).
  • Automatic security updates of the server's operating system; no password log-in over SSH to the server's root account; the intrusion-prevention service fail2ban is active on the server.
  • A process for regularly testing the effectiveness of the measures. Scandora keeps a written list of these measures with the evidence for each and makes it available to you on request (section 4).

8. Controller & Data-Subject Rights

You remain in control of the data. Data subjects have the rights under Art. 15–22 GDPR (access, rectification, erasure, restriction, portability, objection). Scandora assists you in fulfilling them. To exercise rights or raise questions, contact privacy@scandora.eu.

Where that assistance is limited. For the GoBD capture and change records described in section 2, the append-only design allows only part of it: we can give access (Art. 15), restrict further use (Art. 18), export the entries (Art. 20) and note an objection (Art. 21), but we cannot rectify (Art. 16) or erase (Art. 17) a single entry while the retention period stated in section 2 runs — and, as section 2 says plainly, today nothing removes these rows once it expires either. Deleting the account replaces the identifiers in every one of its entries, but the entries stay personal data: each chain fingerprint was computed before that replacement, and the capture record's checksum still matches the document itself. For every other record covered by this DPA — history records, the search index, managed-AI content — the assistance is unrestricted.

7. Technische & organisatorische Maßnahmen (TOM)

  • Verschlüsselung in der Übertragung (TLS) auf jeder Verbindung zwischen App, unseren Servern und unseren Unterauftragsverarbeitern.
  • Verschlüsselung der von Ihnen hinterlegten Integrations-Zugangsdaten pro Nutzer (AES-256-GCM). Für die übrigen nach diesem AVV gespeicherten Daten — die Verlaufseinträge, den Suchindex und die GoBD-Erfassungs- und Änderungsaufzeichnungen — führen wir keine Verschlüsselung im Ruhezustand als Maßnahme an: Der Server von Scandora speichert sie lesbar, und sie sind durch die hier genannten Zugriffs-, Trennungs- und Hosting-Maßnahmen geschützt.
  • Trennung je Nutzer: Gespeicherte Einträge werden je Nutzer und Profil getrennt gehalten, und jede Anfrage der App wird gegen das authentifizierte Token der angemeldeten Person geprüft. Die Datenbank selbst beschränkt die Anfragen nach Verlaufseinträgen und nach dem Suchindex auf die Zeilen dieser Person (Row-Level-Security), sodass eine solche Anfrage die Einträge einer anderen Person auch dann weder lesen noch ändern kann, wenn ihr eigener Filter fehlerhaft ist.
  • Zugriff des Scandora-Teams auf Inhalte: Den Inhalt eines gespeicherten Eintrags kann das Scandora-Team nur über eine Administratoransicht lesen, die ein Administratorkonto, eine kurz zuvor bestätigte Anmeldung und für jeden Eintrag einen schriftlichen Grund verlangt. Jeder Zugriff wird in ein Prüfprotokoll geschrieben, bevor der Inhalt gezeigt wird, und nichts wird gezeigt, wenn dieser Eintrag nicht geschrieben werden kann; das Prüfprotokoll ist auf Datenbankebene reine Anfügung. Jede Administratorin und jeder Administrator kann pro Tag nur eine begrenzte Zahl von Einträgen öffnen, und eine ungewöhnliche Häufung von Zugriffen löst eine Warnung aus. Der administrative Zugang zum Server selbst wird von diesem Protokoll nicht erfasst.
  • Administratoranfragen werden abgewiesen, sobald die Anmeldung der Administratorin oder des Administrators widerrufen ist, und zerstörende Administratoraktionen, etwa Löschungen, verlangen zusätzlich eine kurz zuvor bestätigte Anmeldung.
  • Anfragebegrenzungen je Konto und je Netzwerkadresse an den Schnittstellen des Servers, einschließlich des Dokument-Chats.
  • Pseudonymisierung der Nutzerkennung (Firebase-UID); die Protokolle der Dienste von Scandora nennen eine Person nur über ein pseudonymes Kennzeichen; die Sicherheitsprotokolle des Servers (das Zugriffsprotokoll des Proxys vor diesen Diensten sowie die Anmelde-, Sperr- und Firewall-Protokolle) erfassen Internet-Adressen (IP-Adressen) und Uhrzeiten, aber weder die Nutzerkennung noch aufgerufene Seiten oder Abfrageparameter; kein Protokoll enthält Dokumentinhalte, Chat-Fragen oder Antworten.
  • Der Server von Scandora speichert oder protokolliert keine Chat-Fragen oder Antworten und auf dem optionalen Weg zu KI-Modellen außerhalb der EU auch nicht die an Anthropic weitergeleiteten Inhalte.
  • Das Löschen eines Verlaufseintrags entfernt ihn und seine Passagen im Suchindex, und die Kontolöschung löscht sämtliche Verlaufseinträge, den Suchindex und sämtliche Importregistereinträge des Kontos. Die GoBD-Erfassungs- und Änderungsaufzeichnungen werden nach Abschnitt 2 aufbewahrt und von dieser Löschung nicht erfasst; die Kontolöschung ersetzt stattdessen die Kennungen darin, sodass kein aufbewahrter Eintrag mehr die Kennungen des gelöschten Kontos enthält.
  • Die OAuth-Komponenten, der Endpunkt zur Ausstellung der Zugangsberechtigung, der Suchindex, der Dokument-Chat sowie sämtliche nach diesem AVV gespeicherten Daten werden auf dem eigenen Server von Scandora in Falkenstein, Deutschland, gehostet, mit zwei Ausnahmen, die beide in Deutschland bleiben: Die KI-Modellaufrufe auf dem EU-Weg gehen in die Google-Region europe-west3 (Frankfurt), und das Importregister wird in Google Cloud Firestore in derselben Region europe-west3 gespeichert. Auf dem optionalen Weg zu KI-Modellen außerhalb der EU geht der KI-Modellaufruf über den Server von Scandora an Anthropic in den USA (Abschnitt 6).
  • Automatische Sicherheitsupdates des Server-Betriebssystems; keine Passwort-Anmeldung per SSH am Root-Konto des Servers; der Dienst zur Einbruchsabwehr fail2ban ist auf dem Server aktiv.
  • Verfahren zur regelmäßigen Überprüfung der Wirksamkeit der Maßnahmen. Scandora führt eine schriftliche Liste dieser Maßnahmen mit dem Nachweis für jede und stellt sie Ihnen auf Anfrage zur Verfügung (Abschnitt 4).
